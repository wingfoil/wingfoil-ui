## Summary

When a project defines a directive id both in `directives/custom/` and in `directives/built-in/`
(the custom file wins in WingFoil), the Directives view shows extra rows and a wrong order instead
of one row per directive.

## Steps to Reproduce

1. The `custom` e2e fixture after the packs adoption of `governance-alignment-rel-v0.3-plan` step 3:
   its `.wingfoil/` has a custom `definition-of-done` overriding the built-in one of
   `methodology/scrum`.
2. Open the console on it and open the Directives view; choose "only mine", then "all".
3. Compare the rows with `wingfoil directives list --format json` of the same project.

## Expected Behavior

One row per directive id — the one in force, as WingFoil resolves it (the custom file wins); a
shadowing warning, if any, shown as text.

## Actual Behavior

Extra, repeated rows in a wrong order: R-06.1 ("Filter the directives bound to my role") and R-06.2
("Show every directive with all") fail on Chromium, Firefox and WebKit
(`expect(locator).toHaveText` with 3 more rows than expected).

## Evidence

- The full e2e run of the adoption gates (step 3, design branch of the pre-step): R-06.1 failed on
  the three engines and R-06.2 on Firefox; the other Directives scenarios (R-06.3, R-06.4) passed.
- `web/src/directives/DirectiveList.tsx:112` keys each row by `key={e.frontmatter.id}`; two entries
  of the list share that id when a custom directive overrides a built-in one.

## Notes

- Suspected cause: duplicate React keys, and/or the list rendering every entry of `directives list`
  instead of the one in force; to be confirmed at the fix task's design (`directiveInForce` in
  `server/src/reads/project-reads.ts` already selects the one in force for a single directive).
- It affects every project that overrides a built-in directive, so it is in v0.2.0 as released; the
  packs adoption only exposed it in this repository's tests.
- Proposed fix release: v0.3, through a governance fix task before the step-3 merge.
