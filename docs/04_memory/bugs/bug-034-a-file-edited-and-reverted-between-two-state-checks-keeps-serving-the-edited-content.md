## Summary

The console keeps the reads of one repository state (`memory.yaml`, element files, `ui.yaml`) under
that state's key. A file edited, read by a request, then reverted before the next state check gives
the old key again: no `repo` event fires and the cache keeps serving the values read from the edited
file until the state changes again.

## Steps to Reproduce

1. A project the console shows; a state check marks a file (e.g. `.wingfoil/ui.yaml`) with content A,
   state key K_A.
2. Save content B in the file and, before the next check (the watcher's check runs about 1.5 s after
   a change), request a view that reads it (e.g. `GET /api/p/:pid/config`): B is read and kept under
   K_A.
3. Revert the file to A before that next check.

## Expected Behavior

Every value served under a state key is read from the bytes that state stands for: after the revert,
the console serves A.

## Actual Behavior

The next check computes K_A again (`server/src/snapshot/snapshot.ts`, `runCheck`), so the memo of
`view()` (one state, keyed by `contentKey`) is kept and serves B until another change moves the key.
The state check marks a file's bytes, but a later read under the same key reads the file again,
with no tie to the bytes the check saw.

task-068's security-adversarial review, round 1, finding 6 (2026-11-06): the sequence above traced
