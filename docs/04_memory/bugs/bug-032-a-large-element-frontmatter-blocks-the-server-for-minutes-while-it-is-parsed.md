## Summary

Parsing an element's frontmatter costs time that grows with the square of its size: a frontmatter
of 1 MiB of keys blocks the server's event loop for about 99 s, one of 5 MiB for about 40 minutes.
The cause is the YAML library's default duplicate-key check (`uniqueKeys: true`), the same one
task-054 turned off for `ui.yaml` (D54-3).

## Steps to Reproduce

1. An element file whose frontmatter holds many keys, `k1: v1` … `kN: vN`, for 1 MiB in all,
   committed to a project the console shows.
2. Open the element's panel (or any read that parses its frontmatter).

## Expected Behavior

A frontmatter of any size is parsed in time linear in its size (a few hundred milliseconds for
1 MiB), and a duplicate key is still refused with its line.

## Actual Behavior

`parseYaml` (`server/src/reads/frontmatter.ts`, `parse` with `merge: true` and the library's default
`uniqueKeys: true`) takes 634 ms for 64 KiB, 7.1 s for 256 KiB and 98.9 s for 1 MiB; the same texts
parse in 167 ms, 435 ms and 885 ms with `uniqueKeys: false`. The server answers nothing else while
it parses. A 5 MiB list of items takes 4.2 s, a 5 MiB string 834 ms, a 5 MiB body 13 ms: only many
keys trigger it.

## Evidence

task-055's design, probe P4b (`docs/04_memory/v0.3/task-055-shared-reference-index-held-gates-and-descriptor-rules.md`,
section *design (2026-11-06)*, commit `d2a60845` on its task branch).

## Notes

Found by task-055's design probes (2026-11-06), outside its diff; opened on the approver's OK
("055: … q3-a", 2026-11-06). The largest frontmatter in this repository is about 2 KiB; reaching
the defect needs an element file pushed by someone with push access. task-055's reference index
would read every element of a project and hit it on every state change, so task-055 absorbs the
fix: `uniqueKeys: false` with a linear duplicate-key check (as D54-3) and a 64 KiB bound on the
frontmatter the index reads.
