## Summary

The notification bell's *Updates* list keys each row by the event's commit (`key={e.sha}`,
`web/src/shell/NotificationBell.tsx`), but one commit can give several Memory events (spec-002 §3
rule 1: a grouped subject gives one event per id, all with the same sha), so such a commit gives
React duplicate keys and the list can show a duplicated or a missing row after a re-read.

## Steps to Reproduce

1. On a project on WingFoil 0.3.1, make one commit that changes two Memory elements with a grouped
   subject, so `GET /api/p/:pid/events/memory` answers two events with the same `sha`.
2. Open the notification bell's *Updates* list, then make a newer Memory commit outside the UI so
   the list re-reads (`repo` event).

## Expected Behavior

One row per event, in the server's order, before and after the re-read.

## Actual Behavior

React warns of two children with the same key, and after the re-read the list can keep a stale row
or drop one of the two events of the grouped commit.

task-080-recent-activity-on-today's review round 1 (2026-11-16, `3f4515fd`), finding F-1: the same
key in task-080's Recent activity card gave 4 rows instead of 3 after a re-read in
`test/web/today/recent-activity.test.tsx` (the test with two events of one commit), fixed there by
the key `${sha}:${id}` (`eaa288d1`). The bell's key, at `web/src/shell/NotificationBell.tsx:241`
(`<UpdateItem key={e.sha} …>`), predates task-080 (task-042, v0.2) and was left untouched by it.
