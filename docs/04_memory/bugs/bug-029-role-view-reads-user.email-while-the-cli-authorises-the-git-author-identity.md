## Summary

The console's identity read (project header, role view) uses `git config --get user.email`, while
the WingFoil CLI authorises git's author identity, resolved as `git commit` does
(`GIT_AUTHOR_*`, then `author.*`, then `user.*`): with author variables in the console's
environment the UI offers actions the CLI then refuses.

## Steps to Reproduce

1. A project whose `user.email` is an approver member of its `dna.yaml`.
2. Start the console with `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL` (and `GIT_COMMITTER_*`) set to a
   non-member identity in its environment — as an agent session's environment does since task-050.
3. Open a pending element.

## Expected Behavior

The project header and the role view show the identity the CLI will authorise (git's author
identity), so no Approve or Reject is offered to a non-approver.

## Actual Behavior

They show the approver read from `user.email` (`server/src/identity/git-email.ts`,
`GitReads.email()`); Approve is offered and the CLI refuses it: 422 `cli-refused`, `user not
authorized to approve type 'task'`. Nothing wrong is written.

## Evidence

- `server/src/identity/git-email.ts` reads `git config --get user.email` only; the CLI resolves the
  author from the environment first (`wingfoil-cli` W-39; the `GIT_TRACE` of `memory approve` in
  task-050's design).
- `gitEnv` keeps `GIT_AUTHOR_*`/`GIT_COMMITTER_*` for the CLI child (pinned by
  `test/server/process/git-env.test.ts`, task-050 Q1-A).
- task-050's Execution Notes, `### design`, finding F2.

## Notes

Found by task-050's design (2026-11-04); opened on the approver's OK (task-050 Q2, 2026-11-05).
Fix direction: read the identity as `git commit` resolves it, e.g. `git var GIT_AUTHOR_IDENT`,
keeping the read-only rules of the console's git reads (no fsmonitor, no transport).
