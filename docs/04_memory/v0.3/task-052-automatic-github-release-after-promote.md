## Description

Governance task of `minor-v0.3`, Wave 0 (dl-009 action 5; `docs/publishing.md` *GitHub Release*:
"an automatic `release` job like WingFoil's … is planned for v0.3"). The GitHub Release of `v0.2.0`
was made by hand on the approver's OK (2026-10-20). `.github/workflows/publish.yml` gains a
`release` job after `promote` that creates the GitHub Release of the tag: the CHANGELOG section as
notes and, as assets, the smoked tarball and the **coverage totals only** — the full coverage
reports hold absolute local paths (dl-005), so they are never attached.

A tag run's `promote` only stages the version: it waits in npm's stage queue until the approver's
`npm stage approve` with 2FA (`docs/publishing.md` *The pipeline*). The job must not announce a
version that is not live; how it waits for that is a design choice for the approver (AC-1).

**Backlog items:** GOV (governance — dl-009 action 5: the automatic GitHub Release after
`promote`)

## Acceptance Criteria

- **AC-1 — Design decision.** The design proposes, and the approver decides, how the Release
  relates to the live version: e.g. (a) a **draft** Release created after `promote`, made public by
  the approver after `npm stage approve` (`gh release edit --draft=false`); (b) a job that waits for
  `npm view wingfoil-ui@X.Y.Z version`, bounded, in an environment the approver approves after the
  stage approval; (c) another trigger. The decision is quoted in the Execution Notes and in
  `docs/publishing.md`.
- **AC-2 — The job.** `release` `needs: promote`, runs only when `promote` runs (a `vX.Y.Z` tag
  push; never on `workflow_dispatch`), pins every `uses:` by full commit SHA with its tag in a
  comment, holds the only `contents: write` of the workflow (every other job keeps `contents:
  read`; `id-token: write` stays `promote`'s alone), reads no secret beyond the job's
  `GITHUB_TOKEN`, and has a `timeout-minutes`. Notes: the CHANGELOG section of the version with its
  relative links made absolute to the tag (as the hand-made `v0.2.0` Release). Assets: the tarball
  `stage` smoked (the gate's artifact, the same bytes) and a coverage-totals file built on the
  runner from the gate's `test:coverage` (the `total` figures only: lines, statements, functions,
  branches), passed between jobs as an artifact — no `coverage-final.json`, `clover.xml` or any
  per-file entry.
- **AC-3 — Invariants frozen.** `test/package/publish-workflow.test.ts` gains the job: the chain
  `gate → stage → promote → release`, the `if` of the job, its permissions (and that no other job
  writes), its pinned actions, and that the coverage asset holds no path (red first on the current
  workflow). A test of the totals extraction (its script or step) shows a summary with per-file
  entries reduced to the totals, with no path left.
- **AC-4 — No run, no registry write by the agent.** The agent pushes no tag, writes nothing to
  the npm registry and triggers no Actions run for this task: the wave dispatch of dl-011 (a
  `workflow_dispatch` of `publish.yml` on `main` at the wave gate, the approver's standing OK) is the
  only run, and it never reaches `promote` or `release`; the first real run is the `v0.3.0` tag
  run, with the approver.
- **AC-5 — Docs.** `docs/publishing.md` — *The pipeline*, *Every release* (the approver's steps
  around the Release), *GitHub Release*, the row *After the stage* of *Differences from WingFoil's
  pipeline* — and the header comment of `publish.yml` describe the job; `CLAUDE.md` *Project status*
  ("an automatic one is planned for v0.3") updated; Version/Date bumped.
- **AC-6 — Gates.** `typecheck`, `lint`, `format:check`, `test:coverage` (≥ 80 %),
  `npm run test:publish-smoke` (the workflow changes: `CLAUDE.md` *Checks*), each through the
  machine-free slot with load and slot wait in its log; `npx vitest run test/docs test/package`.

## Implementation Notes

- Read at design: `docs/publishing.md` (all), `publish.yml`, `test/package/publish-workflow.test.ts`,
  task-029's Execution Notes (the pipeline, D29-x), dl-004, dl-005; WingFoil's own `release` job
  (public repository `wingfoil/wingfoil`, `.github/workflows/publish.yml`), which the table of
  `docs/publishing.md` compares.
- The coverage totals need a summary reporter on the runner (e.g. Vitest's `json-summary`); adding a
  reporter must not change the local `test:coverage` output agents read, nor write a report holding
  paths into anything uploaded.
- Security: the job is the workflow's only write to the repository (a Release and its assets);
  a security-adversarial reviewer who runs the tools reviews it (permissions, pinned actions, the token's scope, no
  `pull_request_target`, no input from the event body in a `run:` line).
