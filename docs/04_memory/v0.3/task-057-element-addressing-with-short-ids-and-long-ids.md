#### Probes

All on scratch repositories built with the pinned CLI (`wingfoil@0.3.1`, Kanban template, the
harness's isolated git configuration and identities), outside the repository, removed afterwards.

- **P1 — ids WingFoil makes from long titles.** `memory add --type task --title` with 60 words:
  exit 1, `{"error":"ENAMETOOLONG: name too long, open '<absolute path>/task-001-word-…-word.md'"}`
  — no element, no commit, the number not consumed. WingFoil caps nothing: the longest id it can
  write is 252 characters (`<id>.md` = 255 bytes). A title with non-ASCII letters (`Caffè über
  naïve 日本 Ünïcødé`) gives `task-001-caff-ber-na-ve-n-c-d-test`: the slug is ASCII only, so an id
  made by `memory add` never holds a multi-byte character. A title of ASCII words gave a
  252-character id (file name 255 bytes); `memory search` lists it, `memory history` answers its
  three entries; `memory history task-002` answers `document not found: task-002` (0.3.1 takes no
  short id, spec-011 §1).
- **P2 — the writes of a 252-character id** (`GIT_TRACE=1`, a `git` wrapper first on the `PATH`
  writing each child's argv and environment, `.git` listed with hashes before and after): `memory
  submit` and `memory approve --reason` exit 0. Every git child gets the full id, only as argv —
  the path `docs/memory/task/<id>.md` after `--` in `status --porcelain`, `ls-files -s -z`, `add`,
  and in `git show <sha>:<path>`; the full id in the `commit --only -m` message. No environment
  variable holds the id (the two matches were the multi-line `-m` argument); the children's `GIT_*`
  are the configuration ones plus `GIT_AUTHOR_NAME`/`EMAIL` of the committer on the `commit`
  only. Subjects, whole (git truncates nothing): `wf(task): submit <id>` (no bracket on 0.3.1),
  `wf(task): approve <id> [pending → approved]` with the `Approver:`, `Reason:` and
  `WingFoil-Version:` trailers. `.git`: no file added or removed besides objects (12 objects
  added); `index`, `HEAD` and `main` logs, `refs/heads/main`, `COMMIT_EDITMSG` changed (and
  `config`, by the probe's own identity switch). Each commit runs `git maintenance run --auto`
  (known since task-033). So the server's exact match of the write's commit (spec-004 §5) holds
  with the full id, and no length reaches a shell or a file name the server builds.
- **P3 — the router** (Fastify 5.12.5, `find-my-way` 9.9.0; a scratch app with `app.ts`'s
  `frameworkErrors` order, the not-found handler, the `@fastify/static` wildcard and an `onRequest`
  guard, routes of the five `:eid` shapes). Today, a parameter over 100 characters: without a web
  build every route answers 400 `invalid-request` (`FST_ERR_MAX_PARAM_LENGTH` through
  `frameworkErrors`); with a web build a `GET` falls to the static `/*` route and answers 404

  `..%2F..%2Fetc` and `task-001%2Fx` reach the handler decoded (`../../etc`, `task-001/x`), as

#### Decisions

- **D57-1 — the short-id rule** in a new pure module `server/src/reads/short-id.ts`:
  `shortIdOf(id: string, idPattern: string | undefined): string | undefined` — the index of the
  first `{n}` in the pattern; `L` the text before it, non-empty and holding no `{`; `id` starts with
  `L`; then a scan of ASCII `0`–`9` from `L.length`, at least one; the answer `L` + the digits (the
  longest run). No `RegExp` is built from a pattern or an id; the work is linear in the two lengths.
  A short id equal to the full id (`sprint-001`) is still the element's short id and is served
  (AC-1, spec-011 §1's example); resolution step 3 skips those elements (steps 1–2 find them). The
  pattern is `memoryYaml.types[match.type]?.id_pattern`: an undeclared type, a type with no
  pattern or an unreadable `memory.yaml` → no short id; `shortId` is then **absent**, never `null`.
  `shortIdsOf(memoryYaml | undefined): (match: { id; type }) => string | undefined` wraps it for
  the routes (and for spec-012's `ElementRef`, its own task).
- **D57-2 — where `shortId` is served:** `element.shortId` of the element read, each row of
  `/elements` (with `?archived=true` too) and `element.shortId` of the Today rows (built in
  `todayOf`, once per state as today); from the state's cached `memory.yaml` read (a direct read,
  memoised: no new process, TT-PERF-05 and the process audits unchanged). Not in the history body,
  the write responses or the Memory events.
- **D57-3 — resolution** in a new module `server/src/http/element-address.ts` (to keep the edits
  of `project-routes.ts`, which task-056 also changes, to two call sites):
  `resolveElement(view, eid, shortIds)` → the full id, `{ ambiguous: matches }`, or none; then the
  element read goes on as today with `view.element(fullId)`. Comparisons are `===` on strings; the
  archived lists come only from `view.archivedElements(status)` (memoised per state). The order is
  spec-011 §3's — see Q1, which decides whether the archived full-id step runs before the live
  short-id step.
- **D57-4 — the 409** (spec-011 §3, E4): `{ error: { code: "ambiguous-id", message: "Ambiguous
  id", detail: { candidates: [{ id, shortId, title, type, status }], more } } }` — the candidates of
  one step only (live, or archived), ordered by full id with code-unit order (`a < b`, not
  `localeCompare`: no locale), the first 20, `more` = the rest (0 when none, always present);
  `title` through `neutralise` (`server/src/git/redact.ts`; task-056's serialiser helper if it
  merges first — W0-7 resolves it on this branch); `id`, `type`, `status` as `memory search`
  answers them (spec-004 §5). Thrown as the routes' `Refused`, so `X-Repo-State` is set as on every
  read. The 404 stays `{ error: { code: "not-found", message: "Not found" } }`, no `detail`.
- **D57-5 — history and writes: the full id only, unchanged code.** History's `findMatch` (live,
  then archived, full ids) and the writes' `listed` (live full ids) already answer 404 to a short

  `routerOptions` form: Fastify 5 deprecates the router options' top-level access, FSTDEP022);

#### Open questions

- **Q1 — spec-011 §3's order contradicts its own E3 clause.** Step 2 (an archived element's full
  id) comes before step 3 (a live short id), so a short-id read must run the two archived searches
  before it can answer even when a live element matches — yet step 4 says "the two lazy archived
  searches run only then" and AC-2 asks for "no archived search started when one does". Options:
  (a) keep the order of steps 1 → 2 → 3 → 4 (a full id always wins, every listed element reachable
  by its full id); the archived searches run at most once per repository state on a read whose
  `:eid` is no live full id — as they already do for an unknown id today; AC-2's clause and step 4's
  parenthesis read "no archived **match** is chosen when a live one matches" (a spec-011 Process
  Note); (b) reorder 1 → 3 → 2 → 4: no archived search when a live short id matches, but an
  archived element whose full id equals a live element's short id would be answered as the live
  element (the wrong element, also when opened from the Memory list); (c) as (a), plus the
  archived searches skipped when no archived list is needed by any type — not decidable without
  the searches, so no saving. **Recommendation: (a)** — correctness over two memoised processes
  on an address-only path (the page reads by full id after the canonical rewrite, spec-011 §2).
- **Q2 — "characters" in spec-011 §4 are UTF-16 code units** of the decoded parameter (P3: an
  astral character counts 2). Ids WingFoil makes are ASCII (P1), and 252 is the file-name maximum
  for them. Options: (a) a Process Note in spec-011 stating the unit, tests at 255/256 code units
  with ASCII, `é` and an astral character; (b) count code points with a custom check before the
  router — more code for ids WingFoil cannot make. **Recommendation: (a).**
- **Q3 — the WingFoil gap of P1** (`memory add` of a long title fails with a raw `ENAMETOOLONG`
  quoting the absolute path; no cap on the slug). A feedback note needs a `wingfoil-cli` entry
  (its first line `Reports W-NN.`, `test/wingfoil-feedback.test.ts`), which is a `.wingfoil/`
  change (W0-15). Options: (a) the coordinator records W-46 and a note F-038 through a
  `governance-evolution` run, outside this task's diff; (b) both in this task, its `.wingfoil/`
  part through that run; (c) nothing. **Recommendation: (a)** — it is not this task's behaviour
  (the console has no `memory add` until v0.4) and keeps this branch free of `.wingfoil/`.
