## Context

dl-013-git-worktrees-of-a-repository-read-as-one-project (ready) reads a repository's git worktrees
as one project: the main checkout first, an element URL resolved in every worktree, the branch shown
for each element that is not on the main checkout. dl-021-scope-and-order-of-the-releases-from-v0.3.1-to-v0.4.1
puts it in v0.3.3, whose `release-planning` turns it into tasks; no task exists yet.

The approver asked on 2026-11-26 for two points of it to change first. The case they come from: a
project whose checkout is not on its base branch (this repository's own line is on
`design/dev-loop_v0.3.1`), with task worktrees on further branches. Labelling every element that is
not on the main checkout would label almost all of them, the ones that reached the branch from the
base branch included.

## Decision

dl-013 is amended by A and B; the rest of it stands.

**A. The branch label.**

1. An element carries a branch label only when its file changed on that branch after the branch's
   merge-base with the project's base branch. An element that reached the branch from the base
   branch, before or after the branch was created, carries none.
2. The base branch is, in order: a setting of the project's UI configuration (`.wingfoil/ui.yaml`),
   when present; otherwise the remote's default branch (`refs/remotes/origin/HEAD`: `main`,
   `master`, `trunk` or another); when neither resolves, no branch label at all, and the project
   page says why.
3. The rule applies to the main checkout too: when it is not on the base branch, its elements are
   labelled by the same rule.

**B. The same element on another branch or worktree.**

1. **The element stays.** Choosing another branch or worktree on an element page shows the same
   element in that copy. Where the element does not exist, the page answers *not on `<branch>`* (a
   not-found state of the page, not a redirect to the list), so one element URL keeps one form
   across copies (dl-013, with dl-012-console-links-for-agents-across-projects's short ids).
2. **The most recent copy is marked.** The branch and worktree selector says in which copies the
   element exists and marks the most recent one: a copy with uncommitted changes to the element's
   file is the most recent; otherwise the copy whose last commit touching the file is the newest
   (commit date); copies holding the same blob are equal, and none of them is marked over the
   others.

**Unchanged.** dl-013's constraints: a worktree is read after the same checks as a folder the user
adds, on the path git reports, through the sanitiser of tool-sourced text; the main checkout stays
the project's default for reads, events and governed writes; the cold-read budget is counted per
worktree; elements on other worktrees are read-only until planning decides otherwise.

**Out of scope.** Several clones of one repository as one project: dropped (the approver,
2026-11-26). The console keeps one folder per project; which folder it is, the launcher decides,
outside the UI.

## Rationale

- A label that marks what differs from the base branch says where work is in flight; a label on
  every element of a non-base checkout says nothing.
- The base branch is not always `main`: the project's own setting first, then what the remote
  declares, and no guess when neither answers.
- Keeping the element page on a branch switch, with a not-found state, keeps dl-013's one element
  URL across copies; a redirect to the list would lose the element the user asked for.
- Marking the most recent copy answers "which one is current" without the user comparing copies;
  equal blobs are not ranked, so the mark never rests on a tie.
- Trade-off: the merge-base and the per-copy reads add git calls to a cold read; they count in the
  per-worktree budget dl-013 keeps.
