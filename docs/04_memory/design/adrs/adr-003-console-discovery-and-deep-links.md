## Context

dl-012 accepts three requests from the WingFoil maintainer so that the agents of WingFoil projects
can cite Memory elements as links to a locally running console (`/p/<project id>/e/<element id>`).
Two of them are architectural and are decided here; R2 (short element ids) belongs to spec-011.

- **R1 — discoverable address.** Without `--port` the operating system chooses the port
  (spec-007 §1), and nothing on disk says where a console runs: the state directory holds only
  `state.json` (spec-006 §1). An agent cannot build a link.
- **R3 — deep links across restarts.** A link opened in a browser whose session the console no
  longer knows shows "This page is no longer recognised by the console"; after the user opens the
  new console URL, they land on the start page, not on the requested one.

Forces:

- **The session model of adr-001 D8 and spec-004 §2** (REQ-SEC-02): a new random token per start,
  carried only in the fragment of the printed URL, exchanged for an `HttpOnly`, `SameSite=Strict`
  cookie `wfui_session_<port>`; the sessions live in memory and a new start invalidates every token
  and session (X-02.2).
- **dl-012's constraints:** the token never appears in a file, a link or a log; R1 defines the
  behaviour of two consoles on one state directory and its file is readable by the user only; R3
  changes the session model, so it starts with a design spike and its task gets the adversarial
  reviewer who runs the tools (dl-006).
- **No secrets stored** (REQ-SEC-09): the state directory, `ui.yaml` and the logs hold no session
  token, session id, git credential or environment value; spec-006 §5 says the same of `state.json`.
- **Two consoles share one state directory** (spec-006 §4): they keep one project list, coordinated
  by the advisory lock `state.json.lock` (`<hostname> <pid> <nonce>`, stale when its host is this
  machine's and its pid is dead, or after 10 s without a heartbeat).
- **The release budget** (RP3-7, RP3-10): R1 is in v0.3; R3 is implemented in v0.3 only if the spike
  stays small; the reference for a security change of the console is task-046 (six review rounds).

`release-planning` v0.3 decided R1's shape (RP3-14 D4: one address file per console,
`consoles/<port>.json` in the state directory, mode 0600, never a token, stale when its host and
process id do not match, as `state.json.lock`) and placed it in this ADR rather than in spec-006
(RP3-15 F3). Without this decision every agent would scan ports or ask the user for the URL — whose
fragment is the token — and every restart would keep breaking the links already given out.

## Decision

D1–D5 decide R1. D6 and D7 decide R3 — option A of the spike, chosen by the approver (A1, A2);
R3 is implemented in v0.3 by one task with the adversarial reviewer (dl-006). The spike's findings
are in *Appendix A*, the other options in *Alternatives considered*.

**D1 — One address file per console.** A console writes `consoles/<port>.json` in its state
directory (spec-006 §1, the same resolution, `WINGFOIL_UI_STATE_DIR` included). The folder
`consoles/` has mode `0700` and the file `0600` (POSIX). The console creates the state directory
(`0700`) and `consoles/` when missing; an existing `consoles/` owned by the user with group or other
bits is set back to `0700`; one owned by someone else, or a symbolic link, is not used: no address
file, a warning in the log, the start goes on. On Windows no mode is set: the file inherits the
access list of the state directory under `%APPDATA%`, as `state.json` does. The shape (schema
`contracts/state/console-address.schema.json`, no other property):

```json
{
  "format": 1,
  "url": "http://127.0.0.1:4870/",
  "port": 4870,
  "portFixed": true,
  "pid": 41237,
  "host": "<os hostname>",
  "started": "2026-11-03T09:12:44.512Z",
  "version": "0.3.0"
}
```

`format` is the file's own version (a change of meaning bumps it); `url` is always
`http://127.0.0.1:<port>/` — the host of the printed URL, so the browser sends the cookie it set
there; `portFixed` says the port came from `--port` (D7); `pid` and `host` (`os.hostname()`) are
those of the console's process, as in `state.json.lock`; `started` is the UTC time the console
started listening; `version` the package version (`--version`). The file holds no project path or
id (A3).

**D2 — Life cycle.** The file is written **after listening and before the URL line** — between
steps 4 and 5 of spec-007 §3 — so a script that sees the URL line finds the file. It is written
atomically, as `state.json` is (a temporary `consoles/<port>.json.tmp-<pid>-<n>`, unique to the
writer, created exclusively with mode `0600`, `fsync`, `rename`; temporary files of dead processes
are removed at the start housekeeping of D3). While the console runs it refreshes the file's
modification time every 10 s (a heartbeat, as `state.json.lock`'s holder does). When the heartbeat
finds the file gone, or holding another `pid` or `started` (removed or replaced by another console
after a suspend or a stall), it rewrites the file in full, atomically as above, so discovery is
never lost silently. A failed write is a warning in the log, never a failed start: discovery is a
convenience, the console works without it. On stop the file is removed as the first stop step,
right after the console stops accepting connections (spec-007 §6), so no agent hands out a link to
a console that is going away; it is removed again, synchronously and best-effort, by the handler
that runs at any process exit (forced stop, exit 70). A console removes the file only while it
still holds its own `pid` and `started`.

**D3 — Stale files and two consoles on one state directory.** A file is **stale** when its
modification time is older than 30 s (three missed heartbeats), or when its `host` is this
machine's and its `pid` is not a running process (`kill(pid, 0)` fails with `ESRCH`; `EPERM` counts
as running) — as `state.json.lock` judges its holder; a file whose `host` is another machine's is
judged by its age only. The age rule is applied by readers, and by a starting console to other
hosts' files only; it also covers a reused pid: for a reader, the file of a crashed console goes
stale within 30 s, whatever process now holds its pid. Before writing its own file a console
removes the files of **this** host whose `pid` is dead, the other hosts' files older than 30 s and
the temporary files of dead processes (start housekeeping, as for `state.json`) — never a file of
this host by its age, since a suspended or stalled console is still alive (and its heartbeat would
restore it anyway, D2) — and replaces any file already named after its own port: on this host the
port is now its own, whatever the file says (a crash, a reused pid). Two consoles on one state directory listen on two ports, so they
write two files and never contend for one; `consoles/` is not under `state.json.lock`, since each
file has a single writer. Both serve the same project list (spec-006 §4), so a link built on
either opens the same element. A state directory shared by two machines (a network home) is not
supported for discovery: their files may name the same port, and the last writer wins.

**D4 — What an agent does with it.** An agent of a project that cites an element:
1. resolves the state directory as spec-006 §1 does and lists `consoles/*.json`;
2. keeps the files that pass the schema, whose `host` is its own machine's and that are not stale
   (D3: its `pid` running and its modification time within 30 s) — the liveness check, which is
   also v0.3's only measure against links that reach another program on a reused port (A5);
   prefers a console with `portFixed: true` (its links survive a restart, D7), then the most
   recent `started`;
3. finds its project's id in the project list of `state.json` (schema
   `contracts/state/state.schema.json`), by its repository root, read-only, against that schema
   (A3);
4. cites `<url>p/<project id>/e/<element id>`, the URL forms of spec-011; with no live console, it
   cites the id without a link.
The agent never calls the API (it has no token and must not ask for one), never writes in the
state directory, and never treats the file as proof that the page will open: the browser's own
session decides that (D6).

**D5 — What the file never holds.** No session token, no session id, no part or hash of either;
no project path, project id or project list; no environment value, git identity or credential;
nothing a request needs to authenticate. Its content is what `ss -ltnp` already shows the user
about their own processes (a port and a pid) plus the package version. The secret scan of
REQ-SEC-09 covers `consoles/`.

**D6 — R3, recover in place (A1).** The lost-session page stops being
final for a console that is running again on the **same origin**. A page that got a 401 (spec-004
§2) shows the lost-session notice, keeps its own address (path and query — the requested element),
and recovers when the browser holds a valid session again:
- a tab whose token exchange succeeds (`POST /api/session` 204) posts a message with no content on
  the same-origin `BroadcastChannel` `wfui-session`;
- a lost page, on that message, when it becomes visible again and at most once per focus, asks
  `GET /api/server` with its cookie (one probe at a time, with the 10 s timeout of
  `watchFragmentToken`); an OK answer reloads the page on its own address, a 401 leaves the notice;
- the notice says "Open the URL printed in the terminal in any tab of this browser; this page
  reconnects by itself" (catalogue `shell.session.lost.body`).
No token, session id or path crosses tabs or reaches a file, a link or a log; nothing is added to
the URL — no `next=` parameter, so no redirect, open or otherwise. The default `--open` (spec-007
§4) opens the new console URL at start, so in the usual case the user does nothing: links opened
after the start work directly (the browser holds the new cookie), links opened before it recover
when it opens. The rule "a failed exchange is final" of bug-016 (W3-7, S2-8) is kept for the token
path: recovery is a probe with the cookie, never a retried exchange.

**D7 — R3 needs a stable port (A2).** The origin of a link includes its
port, and the cookie's name carries it (`wfui_session_<port>`); a console restarted on another port
is another origin, where no link given out before can work. In v0.3 deep links across restarts are
promised **with `--port`** only; the address file says so (`portFixed`) and `docs/cli-reference.md`
documents it. A default fixed port is reconsidered at v0.4 (A2).

**Spec and contract amendments implied** (each made by the task that implements it, not here):
- spec-006 §1: the state directory holds `state.json` and the folder `consoles/` (`0700`), each
  `<port>.json` `0600`, created and removed by consoles only; §4: `consoles/` is outside
  `state.json.lock` (one writer per file) and its housekeeping at start; §5: the address file holds
  nothing of D5, the secret scan covers it; §6: unit tests of write, heartbeat (it restores a
  removed or replaced file), replace, remove,

  after the stop line.

- `docs/cli-reference.md`: the address file for scripts and agents (D4), deep links and `--port`

## Consequences

- **Positive**
  - An agent can build a working link without the token and without asking the user; scripts get
    the port of a console started without `--port`.
  - R1 adds no secret anywhere: the file is a hint about the user's own process; the session model
    of adr-001 D8 is unchanged by D1–D5.
  - With D6 and D7 a restart costs the user one action at most (usually none, through `--open`),
    instead of one per link, and the requested page is the one that opens.
  - No new endpoint, no persisted session, no change to the token exchange.
- **Negative**
  - The state directory gains a second kind of file, written outside `state.json`'s lock and
    removed at stop: a crash leaves a file behind until the next start's housekeeping; readers
    judge it stale by pid or, within 30 s, by its heartbeat (a reused pid included), and the
    heartbeat is one `utimes` every 10 s per console.
  - D6 reverses W3-7's "lost for good" for the cookie path: the recovery probe must never retry
    an exchange, and the lost page must not keep any state of the dead session.
  - Deep links across restarts need `--port`; without it they still break on restart (D7).
  - Agents read `state.json` to find a project id (A3): its schema becomes something third parties
    rely on.
- **Neutral**
  - The address file follows `state.json.lock`'s stale rule, so the two files age the same way.
  - Windows relies on the access list of `%APPDATA%`, as `state.json` does (A6).
- **Later (v0.4)** — two hardening items found by the spike, outside R1 and R3 (C4):
  - the token in the opener's arguments, readable by other local users through
    `/proc/<pid>/cmdline` on a Linux without `hidepid` while the opener runs (Appendix A, P10);
  - the session cookies sent to every `127.0.0.1` port the browser visits (RFC 6265 §8.5):
    `Secure` / `__Host-` cookies on loopback, after a browser probe (A5).

### Alternatives considered

For R1:
- **One shared `consoles.json` listing every console** — needs `state.json.lock` or a lock of its
  own, and a crash leaves a wrong list; one file per port has one writer and no lock.
- **The address inside `state.json`** — mixes a process's lifetime with the durable list, and a
  console that crashed would leave it in the user's list; spec-006 §1 keeps `state.json` for the
  list and the settings.
- **A port scan by the agent** — finds other local servers, cannot tell a console from them
  without the token, and gives no version.
- **The address in the file and the token next to it** — rejected by dl-012: the token never
  appears in a file.

For R3 (the spike's options, Appendix A):
- **Option B — persisted sessions.** The console keeps a hash of each session id in
  `<state dir>/sessions/<port>.json` (`0600`), the cookie gets a `Max-Age`, and a restart on the
  same port re-loads them; links work with no action at all. Rejected for v0.3: it contradicts
  REQ-SEC-02 ("a new start invalidates every token and session", whose fit criterion asks a 401 for
  a previous start's session) and spec-006 §5; the session cookie becomes a credential of days,
  stored in the browser profile and sent to every server on `127.0.0.1`, whatever its port (cookies
  do not isolate ports, RFC 6265 §8.5); it needs expiry and a "sign out everywhere". Size **M–L**:
  two tasks, four to six review rounds.
- **Option C — a local ticket channel.** A command (`wingfoil-ui open <path>`) reads the address
  file, asks the console for a one-time ticket (≤ 30 s, bound to the path) over a Unix socket or a
  named pipe in `consoles/` (protected by the folder's mode or the pipe's access list), and opens
  the browser on `<url><path>#ticket=<ticket>`. Works without a fixed port and with no action.
  Rejected for v0.3: the ticket is a credential in a link — in the opener's arguments, readable by
  other users through `/proc/<pid>/cmdline` on a Linux without `hidepid` (Appendix A, P10), and in
  the address bar until it is exchanged; it adds an inter-process channel per platform and a
  command to spec-007. Size **L**: two or three tasks, six or more review rounds.
- **The path through the token exchange (`?next=`)** — not needed: the lost tab keeps its own
  address (D6); a redirect parameter would be an open-redirect surface to defend.

### Appendix A — the R3 design spike

Run on 2026-11-03 against this repository at `6010d91`, two consoles started from the build
(`server/dist` from `tsc -b`, the web bundle from `vite build`) on a throw-away state directory.
The token was read from the URL line into a shell variable and never printed.

**Findings.**

- **(a) What survives a restart today: nothing of the session.** The token and the sessions are in
  memory (`server/src/auth/authentication.ts`: a `Set` of at most 64 random ids, a SHA-256 of the
  token); the cookie has no `Max-Age` (`server/src/http/session.ts`) and its name carries the port
  (`sessionCookieName` in `server/src/http/guards.ts`). After a restart on the same port the old
  cookie and the old token both get 401 (P6b, P6c); a new exchange sets a cookie of the same name,
  which then opens a deep path and the API (P6d). The project list and its ids survive (spec-006),
  so `/p/<project id>/…` stays a valid address.
- **(b) A deep link needs a fixed port.** The origin includes the port; Host and Origin are checked
  against it (P8: another port's Origin gets 403); the cookie of the console on one port is refused
  by the console on another, under either name (P5b, P5c). A link given out before a restart on a
  new port points to nothing, or to whatever listens there.
- **(c) The requested path survives the `#token` exchange already, without a redirect.** The
  bootstrap removes only the fragment and keeps path and query (`stripFragment` in
  `web/src/session/session.ts`); the server answers every non-API path with `index.html`, without a
  session (`setNotFoundHandler` in `server/src/http/app.ts`; P4: a deep path answers 200, the API
  401); nothing reads a redirect parameter (P9: `/?next=…` answers 200, no redirect). The only URL
  that carries the token is the printed one, `/#token=…`; no other link may (dl-012), so the path
  must stay where it is — in the tab that asked for it (D6).
- **Today's manual recovery.** A lost tab reloaded after the new console URL was opened in another
  tab of the same browser and port shows the requested page: a reload without a token is
  `connected` and relies on the cookie (`bootstrapSession`; test "uses the existing cookie when
  there is no token (reload)" in `test/web/session/session.test.ts`), and the browser holds the new
  cookie (P6d). D6 automates this; it is why D6 is small.
- **(d) Channels without the token on disk or in a link.** (1) The browser's own cookie jar, shared
  by the tabs of one origin: the console URL opened once (by `--open` or by the user) gives every
  tab of that origin a session — the channel of D6. (2) A one-time ticket over a local socket or
  pipe protected by the operating system: no token on disk, but a credential in a link (option C).
  (3) A persisted session: a credential on disk, in the browser profile (option B). (4) No
  operating-system mechanism lets a page read a local file or a socket; anything else needs a
  helper process.
- **(e) Threat model.**

| Threat | Today | R1 (D1–D5) | D6 + D7 (option A) | Option B | Option C |
|--------|-------|-----------|-------------------|----------|----------|
| Another local user | token in the opener's arguments while it runs (`/proc/<pid>/cmdline`, P10); loopback ports visible to all; the session cookie is sent to any `127.0.0.1` port the browser visits, where another user's process can receive it and replay it with a forged `Host` header (row *Port reuse after a stop*) | cannot read `consoles/` (`0700`); learns nothing a port list does not show | unchanged | can receive a long-lived cookie by serving a page on any `127.0.0.1` port the browser visits | ticket in the opener's arguments (P10), one-time and short |
| A process of the same user | can read the terminal and the browser profile: out of scope | can read or forge the file: a forged address sends the agent's links elsewhere — out of scope, as today | unchanged | can read the session hashes (not usable) and the cookie jar (usable for days) | can ask for tickets: as able as the user |
| Browser history | the start URL, its fragment removed after load (`history.replaceState`) | links without a token | unchanged; no new URL | unchanged | the ticket URL, until exchanged |
| Referrer | the fragment is never sent | none | none | none | none |
| Logs | `authorization` and `cookie` redacted; P7: no token in the log or the state directory | the file names no secret; the log line of a failed write names no path content | the probe is an ordinary API call | session ids would need the same redaction | ticket in the opener's line on failure (`Open this URL…`) |
| Open redirect | none (P9) | none | none: no redirect parameter | none | the ticket's path must be validated as a console path |
| Port reuse after a stop | cookies of every console are sent to any `127.0.0.1` port (RFC 6265 §8.5) | within 30 s of a crash, before the heartbeat makes the file stale, a link can reach another program on the reused port (the residual window of D3) | unchanged | the exposure lasts days | the ticket is bound to the console that issued it |

**Options and size.** A — D6 + D7: **S**, one task (web session state, the lost page and its
text, a same-origin `BroadcastChannel`; spec-004 §2, the UX reference, X-02.2 and a recovery
scenario; an e2e restart on the three engines), two or three review rounds with the adversarial
reviewer; no server change. B — **M–L**, two tasks, four to six rounds, and a change of REQ-SEC-02.
C — **L**, two or three tasks, six rounds or more. Against task-046's six rounds, only A is small.
**Recommendation: A** (decided, A1), in v0.3 next to R1, deep links promised with `--port`; B and
C are not needed for dl-012's need once A and R1 are in, and stay out unless a later request asks
for links with no action and no fixed port. **R3 is small enough for v0.3 (RP3-10) in form A only.**

**Probes** (`$SCRATCH` is a throw-away folder; the token and the cookies stay in shell variables,
never printed):

```sh
export WINGFOIL_UI_STATE_DIR="$SCRATCH/state"
node bin/wingfoil-ui.cjs --port 4911 --no-open > "$SCRATCH/a.out" 2> "$SCRATCH/a.err" & PID_A=$!   # P1
TOKEN=$(sed -n 's/.*#token=\([A-Za-z0-9_-]*\).*/\1/p' "$SCRATCH/a.out")
exchange() { curl -s -D - -o /dev/null -X POST -H "Authorization: Bearer $1" "http://127.0.0.1:$2/api/session" \
  | sed -n 's/^[Ss]et-[Cc]ookie: \([^;]*\);.*/\1/p'; }
COOKIE=$(exchange "$TOKEN" 4911)               # P2: 204, set-cookie wfui_session_4911=…; HttpOnly; SameSite=Strict; Path=/
curl -s -o /dev/null -w '%{http_code}\n' -b "$COOKIE" http://127.0.0.1:4911/api/server        # P3: 200
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:4911/p/abc/e/task-001              # P4: 200 text/html
curl -s -w ' %{http_code}\n' http://127.0.0.1:4911/api/server                                # P4b: 401 unauthenticated
node bin/wingfoil-ui.cjs --port 4912 --no-open > "$SCRATCH/b.out" & PID_B=$!   # P5: a second console, same state directory
curl -s -o /dev/null -w '%{http_code}\n' -b "$COOKIE" http://127.0.0.1:4912/api/server       # P5b: 401
curl -s -o /dev/null -w '%{http_code}\n' -b "wfui_session_4912=${COOKIE#*=}" \
  http://127.0.0.1:4912/api/server                                                           # P5c: 401
kill -TERM "$PID_A"; wait "$PID_A"                                  # P6: the stop line printed, exit 0
node bin/wingfoil-ui.cjs --port 4911 --no-open > "$SCRATCH/a2.out" & PID_A2=$!   # P6: restart, same port
curl -s -w ' %{http_code}\n' -b "$COOKIE" http://127.0.0.1:4911/api/server                   # P6b: 401
curl -s -w ' %{http_code}\n' -X POST -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:4911/api/session                                                          # P6c: 401
TOKEN2=$(sed -n 's/.*#token=\([A-Za-z0-9_-]*\).*/\1/p' "$SCRATCH/a2.out"); COOKIE2=$(exchange "$TOKEN2" 4911)
# P6d: COOKIE2 is wfui_session_4911 again; with it the deep path and /api/server answer 200
grep -rl -- "$TOKEN" "$SCRATCH"/*.err "$SCRATCH/state"                                       # P7: nothing
curl -s -w ' %{http_code}\n' -b "$COOKIE2" -H 'Origin: http://127.0.0.1:4912' \
  http://127.0.0.1:4911/api/server                                                           # P8: 403 forbidden-origin
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' 'http://127.0.0.1:4911/?next=https://example.org'  # P9: 200, no redirect
mount | grep ' /proc '; ls -l "/proc/${PID_B}/cmdline"                                          # P10: no hidepid; -r--r--r--
```

Also observed: the state directory is not created by a start that writes nothing (P1: no
directory after the start), so D1 creates it.
