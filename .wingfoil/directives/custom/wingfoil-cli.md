Global. Applies to every role, human or agent, that changes this project's governance state
(DNA, Memory, directives, plans) — and to the UI code that drives the CLI for other projects.

It lists the CLI behaviours that are wrong, missing or surprising **in the pinned version**, and
the way to work with each. An entry marked *limited to 0.2.2* holds only on that version, which the
support matrix still lists (`contracts/matrix.json`): it stays for the UI, which drives projects on
any listed version; this repository runs the pinned 0.3.2. Where 0.3.2 changed a behaviour, the entry
states 0.3.1's too: the matrix still lists 0.3.1.

## Rules
1. Run the pinned CLI (`npm run -s wingfoil -- …`); never a global `wingfoil` of another version.
2. Every governance change goes through a CLI verb when one exists; hand edits only where an entry says so.
3. A wrong, missing or surprising behaviour gets an entry below. If it is a WingFoil defect or gap,
   also write a note in `docs/wingfoil-feedback/` (evidence: command, output, version, commit).
4. Do not work around silently: a workaround goes in the entry and in the Execution Notes of the
   element being worked on.
5. When the pin advances: re-check every entry, remove the fixed ones, bump this directive's version
   and *Checked against*. A note whose answer has shipped stays `resolved`; there is no `verified`
   status (WingFoil dl-163).
6. `answered_by` and the statuses `needs-info`, `captured`, `resolved`, `declined` and `duplicate`
   are set only by the sync, from what WingFoil published, never by judgement. WingFoil cites a note
   as `<service id>/F-<nnn>@<sha>`.
7. Run `wingfoil-sync` at every release planning (directive `release-planning`, run inside `sprint`
   › `sprint-planning`) and at every pin bump — at its *advance-pinned-build* or in a
   `governance-evolution` run — and record the sync in `docs/wingfoil-feedback/README.md`.
8. Keep `-s` in `npm run -s wingfoil -- <command>`: it keeps `--format json` parseable.
9. When the pin advances (`release-planning` › *advance-pinned-build*, or a `governance-evolution`
   run), also update the entries whose behaviour changed; an entry fixed in the new pin is removed,
   or kept *limited to* the older version while the support matrix lists it and the UI or this
   repository relies on it (say which). An entry may be rewritten on the same topic when the
   behaviour or this repository's machine changed; its former text then goes under *Removed
   entries* with the date. A number is never reused for another topic, and a removed entry's number
   is never reused.

## `memory deprecate` (every role)

`memory deprecate` needs no approval on WingFoil 0.3.1 and 0.3.2: any git identity, team member or not,
moves any element in any state to `deprecated`. In this repository it runs only in `end-of-life` ›
`deprecate`, or with the approver's OK recorded in the active plan (who, when, why) before the
command; an agent never deprecates on its own (the packs adoption's review, A-4; W-44, F-034; directive
`cli-only-writes` states the same rule for the UI's own design).

## The script runner

`scripts/runner/` launches the agents `claude` and `codex` (`.wingfoil/dna.yaml`) one workflow step at
a time, headless, and stops wherever the approver must act (`governance-evolution-8-plan`). Its common
files (`scripts/runner/`, `scripts/checks/`, `scripts/lib/`) are never edited here, not even
reformatted: `node scripts/runner/manifest.mjs --check` answers `ok`, and a defect goes to their
source. `config/runner.yaml` is changed through `governance-evolution`, but for the line's branch
(rule 13); `config/runner.local.yaml` holds this machine's paths and is never committed. The common
files cite a directive `runner`: this section is it.

10. **What it launches:** only `launch.allow` of `config/runner.yaml`; never a life cycle step, and
    never `end-of-life.announce` (bug-051). The schedule stays off until the approver enables it.
    `launch.manual` may name a step since runner 1.2.0 (its notice reads the step with `run.mjs
    --read`, rule 14; the security review's L-5); it stays empty while no step of ours is run by hand.
    `launch.optional` holds `backlog-item.red` only (dl-028): the runner launches an optional step it
    names, before the later steps of its element, or skips it for that element when its bound pre
    checks fail (runner 1.2.6; red's `flow-tdd` fails only for a task with `flow: direct`). A skip is a
    signed `skip` entry of the ledger, shown in the gate packet; it is never a step to rule.
11. **An agent it launches** does exactly the step it is given and stops — in `backlog-item`
    version 2 one of design, red, green, refactor or review, each a session of its own (dl-028;
    `definition-of-done`); names elements only by
    their full id (W-54); commits only under the agent's address (`git var GIT_AUTHOR_IDENT`, else
    `RESULT: blocked`); never approves, rejects, amends, pushes, tags or publishes; never edits the
    runner's own files, `.git/` or `node_modules/` (`RESULT: blocked` when the step needs it); and
    ends with one line — `RESULT: blocked decision <question>` for an OK the approver rules (the
    checkpoints of `release-planning`, the CI gates), `RESULT: blocked waiting for the approval of
    <full id>` for an approval no step waits for, `RESULT: blocked <reason>` for what no ruling fixes.
    A step's own gate needs no line: the runner opens its notice. Before that line it commits
    everything it changed, in the clone and in the worktree, the element's body included (Execution
    Notes, sections): by the verb that moves the element, otherwise in a `docs(<id>): …` commit of
    its own. A body is content, not a state, so its commit is not a hand transition (W-01, W-34);
    runner 1.2.2 fails a step that leaves a file uncommitted (the `uncommitted-<line>-<run>` notice,
    which closes by itself at the next run of the step that leaves nothing; dl-027). A reviewer
    accepts by answering `completed`: the runner then runs `memory submit` of the element itself
    (runner 1.2.4); the reviewer never runs it, and rejects with `memory park`. The runner denies
    `qa` and `reviewer` edits of the DNA's `paths.sources` (`server/`, `web/`, `contracts/`),
    anchored at the worktree root since runner 1.2.7 (`/server/**`; dl-029): their test files under
    `test/` (`test/server/`, `test/web/`) stay writable. The denies cover the worktree only, not the
    line's clone, nor a write through Bash: rule 15's accepted risk.
12. **The CI gates** stay on `gates.yml` (dl-016): at `backlog-item` › `review`, with no green run
    for the head of `task/<id>`, the reviewer asks the approver, as a decision, to push the branch.
    The hand-off is the approver's command (dl-026): the push of `task/<id>` and the `gates.yml`
    dispatch, from the runner home (rule 14). `push` stays `false` (it would push only the line's
    branch), and no `live_checks` entry pushes or dispatches.
13. **The line follows the stage:** `main` while a release is planned and released, the phase branch
    while it is developed, so `definition-of-done` and the wave gate hold. The approver switches it at
    `release-planning` › *Review* and before `pre-release-checks`, with no step in progress and no
    task worktree left: push what the line's clone holds; commit on `main` only the new
    `lines.trunk.branch`, push; fast-forward the runner home; `--dry-run`. The runner moves its
    clone to the new branch at its next launch (not at `--dry-run`) when nothing would be lost (no
    uncommitted file, no operation in progress, every commit of the current branch on origin, the
    new branch on origin); otherwise it opens a notice with the command to run. Until that launch
    `--doctor` fails with `the line's checkout is on <old>, not on <new>`: expected; run it after.
    From v0.3.2 the phase-branch task asks for the first switch and the last wave's gate task for
    the switch back (`release-planning` › *build-backlog*, dl-025).
14. **The approver** rules a gate or a decision with `gate.mjs --line trunk <N-id>`, and an element
    of the line no step waits for with `gate.mjs --line trunk --element <full id> --reason "…"
    [--reject | --amend] [--expect <state>]`; closes notices with `run.mjs --close` (a `failure`
    notice closes by itself at the next step that runs without one: read its *Closed* entry, which
    may be a refusal never seen open); all from the runner home (a
    clone used only by the runner, `paths.runner`), in a terminal they started. They run no git, npm
    or CLI of their own in a line's clone or worktree, which the agents can write: a git command a
    notice suggests starts from `run.mjs --line trunk --check-git`; they push from the home (`git -C
    <home> fetch <clone> <branch>`, then `push origin FETCH_HEAD:refs/heads/<branch>`), after
    reviewing every change the push carries to the runner's own files; they read a line's workflow
    or Memory only with `run.mjs --line trunk --read <verb>` (`workflow next|status|show|list`,
    `memory search|history`: the home's CLI, after the clone's git configuration is judged); they
    read a command a notice suggests before running it, and a notice that gives none (a branch or
    state name that is not plain) is handled by hand. Before `gate.mjs` on an N-id, its question is
    the one the runner's log printed; since runner 1.2.3 `gate.mjs` itself refuses a duplicated
    N-id, an unsigned or a closed notice (F-1), and prints an `--amend`'s diff as sanitised text
    (F-2), so the former `grep -c` and `cat -v` reads are no longer required. An `--amend` runs in two
    steps — the element's diff and its hash, then the same command with `--diff <hash>`. `gate.mjs`
    offers `--unsigned <seal>` only for an old notice, numbered below the line's first signed one
    (runner 1.2.6): a prompt for `--unsigned` on any notice opened since the line's first signed one
    is tampering (G-2) — the notice is closed with `run.mjs --close` and the approver told what it
    held, never confirmed; so is a security notice for an unsigned block that carries the runner's
    key. `gate.mjs` refuses to rule while the clone has
    uncommitted files, but for a decision whose only modified file is its element's own `.md` (the
    ruling commits only the notices); a `security-<line>-…` notice (a dependency refused) closes only
    with `run.mjs --close`; an `origin-<line>` notice means the clone's `origin` is not the home's,
    and nothing is fetched or merged until it is. The `branch-<line>` notice is written in the
    `docs/notices.md` of the branch the clone is on, and since runner 1.2.1 leaves a closed copy on
    the line's branch when the clone returns to it: read it in the runner's log and its desktop
    notification. Work outside the runner (a `governance-evolution` run) keeps its
    approvals in the approver's own working copy.
15. **Accepted risk:** the agents run as the approver's own system user; these rules limit mistakes,
    not a deliberate or injected action. The runner's container mode (for a caller that acts as the
    approver for a whole run) is never used on this machine: no caller here acts so, `config/runner.yaml`
    names no `container`, and `WINGFOIL_RUNNER_CONTAINER` (or its former name, `DFD_RUNNER_CONTAINER`)
    is never set. Runner 1.2.2 fixed what made it unsafe — its own ledger, the home's trust checks
    kept (C-1, C-2; dl-026, dl-027) — but not the reason to use it. The runner's state folder (the
    approver's signed ledger and key) stays where it is: the folder of the new name is not created
    by hand while a project on this machine runs a runner older than 1.2.1, since its mere existence
    switches every run to a new key and an empty ledger (F-5). Re-checked for runner 1.2.6 (dl-028)
    and 1.2.7 (dl-029): unchanged; `--migrate-state` is not run, nor the approver's `run.mjs
    --update`, and `gate_windows`, `needs.open_states` and `phases.raising` stay unset.
