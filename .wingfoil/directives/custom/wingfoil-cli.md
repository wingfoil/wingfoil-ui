Global. Applies to every role, human or agent, that changes this project's governance state
(DNA, Memory, directives, plans) — and to the UI code that drives the CLI for other projects.

It lists the CLI behaviours that are wrong, missing or surprising **in the pinned version**, and
the way to work with each. An entry marked *limited to 0.2.2* holds only on that version, which the
support matrix still lists (`contracts/matrix.json`): it stays for the UI, which drives projects on
either version; this repository runs the pinned 0.3.1.

## Rules
1. Run the pinned CLI (`npm run -s wingfoil -- …`); never a global `wingfoil` of another version.
2. Every governance change goes through a CLI verb when one exists; hand edits only where an entry says so.
3. A wrong, missing or surprising behaviour gets an entry below. If it is a WingFoil defect or gap,
   also write a note in `docs/wingfoil-feedback/` (evidence: command, output, version, commit).
4. Do not work around silently: a workaround goes in the entry and in the Execution Notes of the
   element being worked on.
5. When the pin advances: re-check every entry, remove the fixed ones, bump this directive's version
   and *Checked against*. A note whose answer has shipped stays `resolved`; there is no `verified`
   status (WingFoil dl-163).
6. `answered_by` and the statuses `needs-info`, `captured`, `resolved`, `declined` and `duplicate`
   are set only by the sync, from what WingFoil published, never by judgement. WingFoil cites a note
   as `<service id>/F-<nnn>@<sha>`.
7. Run `wingfoil-sync` at every release planning (directive `release-planning`, run inside `sprint`
   › `sprint-planning`) and at every pin bump — at its *advance-pinned-build* or in a
   `governance-evolution` run — and record the sync in `docs/wingfoil-feedback/README.md`.
8. Keep `-s` in `npm run -s wingfoil -- <command>`: it keeps `--format json` parseable.
9. When the pin advances (`release-planning` › *advance-pinned-build*, or a `governance-evolution`
   run), also update the entries whose behaviour changed; an entry fixed in the new pin is removed,
   or kept *limited to* the older version while the support matrix lists it and the UI or this
   repository relies on it (say which). An entry may be rewritten on the same topic when the
   behaviour or this repository's machine changed; its former text then goes under *Removed
   entries* with the date. A number is never reused for another topic, and a removed entry's number
   is never reused.

## `memory deprecate` (every role)

`memory deprecate` needs no approval on WingFoil 0.3.1: any git identity, team member or not,
moves any element in any state to `deprecated`. In this repository it runs only in `end-of-life` ›
`deprecate`, or with the approver's OK recorded in the active plan (who, when, why) before the
command; an agent never deprecates on its own (the packs adoption's review, A-4; W-44, F-034; directive
`cli-only-writes` states the same rule for the UI's own design).
